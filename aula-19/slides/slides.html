O contador como objeto

def Contador() {
    var n := 0;
    var obj := {};
    obj.inc := fn () { n := n + 1; n };
    obj.get := fn () { n };
    obj
}

var c1 := Contador();
var c2 := Contador();
c1.inc();
c1.inc();
c2.inc();
c1.get() + c2.get()        // 3

Temos o básico da OO: identidade + estado + comportamento

⏱ 4 min.

DEMO: exemplos/contador-privado.alg. Mostrar também o alias: var c3 := c1; e que c3.inc() afeta c1.

O “construtor” é só uma função: cria {}, equipa com closures, devolve.

Mas onde está o estado?

Ambiente               Store

ambiente criado no código cliente:
c1 ─────> ℓ₁ ─────> registro { inc ↦ closure₁, get ↦ closure₂ }

ambiente criado por Contador() (capturado pelas closures):
n ──────> ℓ₂ ─────> 2

O que objetos acrescentam a closures simples?

  1. permitem agrupar vários métodos com um mesmo estado
  2. nos dão identidade única a cada objeto (o que faria var c3 := c1;?)
  3. permitem a mutação do estado interno.

⏱ 4 min.

A figura é simplificada. O record guarda só os métodos; n vive em outra localização, alcançável apenas pelas closures. Esse detalhe é o centro da próxima seção.

Resposta: nada de mecanismo novo. O método é uma closure (Unidade 4); a diferença está em como combinamos as construções que já existiam.

Nossa OO suporta duas formas de estado

Campos privados (encapsulamento e information hiding)

def Contador() {
    var n := 0;
    var obj := {};
    obj.inc := fn () { n := n + 1; n };
    obj.get := fn () { n };
    obj
}

Campos públicos

def ContadorPublico() {
    var obj := { n: 0 };
    obj.inc := fn () { obj.n := obj.n + 1; obj.n };
    obj.get := fn () { obj.n };
    obj
}

⏱ 6 min.

DEMO: exemplos/contador-privado.alg e contador-publico.alg.

A célula 2 (!): escrever em campo inexistente cria o campo (é o que fazemos com obj.inc := ... sobre {}), mas o campo novo não tem relação com a variável n capturada. O estado interno continua intacto.

De onde vem a privacidade?

Do escopo léxico.

Não introduzimos nenhuma regra nova: a variável n só existe no ambiente criado por Contador(), e só as closures criadas lá a capturaram.

  • agregação: dados e operações no mesmo lugar
  • encapsular: esconder a representação

⏱ 3 min.

Pergunta antes de revelar: “não há regra de campo privado em algora; de onde vem a privacidade?”

Agregar não é encapsular: ContadorPublico agrega; Contador encapsula. Em algora, o programador escolhe entre as duas representações.

Invariantes

def Conta(inicial) {
    var saldo := inicial;
    var obj := {};
    obj.deposita := fn (v) {
        if v < 0 { saldo } else { saldo := saldo + v; saldo }
    };
    obj.saca := fn (v) {
        if saldo < v { saldo } else { saldo := saldo - v; saldo }
    };
    obj.saldo := fn () { saldo };
    obj
}

invariante: saldo >= 0, para todo programa que usa a Conta.

E se o saldo fosse um campo público? Se usássemos c.saldo := -1000?

⏱ 4 min.

DEMO: exemplos/conta-invariante.alg. Mostrar o ataque na versão pública.

Com saldo privado, o invariante é propriedade da conta. Com saldo público, vira promessa de todos os usuários da conta.

Método destacado

var c := Contador();
var f := c.inc;        # o método, sem o objeto
f();                   # 1
f();                   # 2
c.get()                # 2

Por que isso funciona?

Cada método é um closure: o ambiente de criação já foi fixado.

⏱ 3 min.

DEMO: exemplos/metodo-destacado.alg. Não há “objeto atual” a descobrir na chamada: ele foi fixado na criação. Escopo léxico de novo.

Herança e polimorfismo, sem class (parte 1)

def Animal(nome_dado) {
  var obj := {};
  var nome := nome_dado;
  obj.voz := fn () { SOM_GENERICO };
  obj.fale := fn () { obj.voz() };    # chama voz dinamicamente
  obj.diga_nome := fn () { nome };
  obj
}

var animal := Animal(1);
animal.fale()

Herança e polimorfismo, sem class (parte 1)

Como codificar herança em Algora:

def Cachorro(nome) {
  var obj := Animal(nome);       # pai cria o registro
  obj.voz := fn () { LATIDO };   # filho muta o MESMO registro
  obj
}

def Gato(nome) {
  var obj := Animal(nome);       # mesmo padrão
  obj.voz := fn () { MIADO };
  obj
}

O código

var SOM_GENERICO := 1;
var LATIDO := 2;
var MIADO := 3;

def Animal(nome_dado) {
  var obj := {};
  var nome := nome_dado;
  obj.voz := fn () { SOM_GENERICO };
  obj.fale := fn () { obj.voz() };
  obj.diga_nome := fn () { nome };
  obj
}

O que é importante aqui? Observe onde os métodos fale e voz são escritos e sobreescritos. Observe onde voz é chamado.

def Cachorro(nome) {
  var obj := Animal(nome);
  obj.voz := fn () { LATIDO };
  obj
}

def Gato(nome) {
  var obj := Animal(nome);
  obj.voz := fn () { MIADO };
  obj
}

var animal := Animal(1);
var cachorro := Cachorro(2);
var gato := Gato(3);

animal.fale()
+ cachorro.fale() * 10
+ gato.fale() * 100
# -> 321

Ligação tardia (late binding)

var g := Gato();
var c := Cachorro();

g.fale();        # 3 (MIADO)
c.fale();        # 2 (LATIDO)

O método fale foi escrito em Animal, mas ele invoca obj.voz() que só é corretamente definido nos registro das subclasses (Gato e Cachorro).

Observe que este mecanismo permite que uma classe mãe (Animal) invoque métodos específicos de subclasses, mesmo que estas tenha sido escritas depois da classe da mãe. A isto se chama late binding e é uma das marcas da herança da OO.

O outro caminho: tipos algébricos (parte 1)

type Animal = Generico(nome) | Cachorro(nome) | Gato(nome)

let som_generico = 1 in
let latido       = 2 in
let miado        = 3 in

# operações (funções separadas dos dados)
let voz = fn (a) =>
  match a {
    Generico(_) => som_generico
    Cachorro(_) => latido
    Gato(_)     => miado
  }
in

let fale = fn (a) => voz(a) in

O outro caminho: tipos algébricos (parte 1)

# "instâncias" (valores imutáveis)
let animal   = Generico(1) in
let cachorro = Cachorro(2) in
let gato     = Gato(3) in

fale(animal)              # -> 1
+ fale(cachorro) * 10     # -> 20
+ fale(gato) * 100        # -> 300

# -> 321

O problema da expressão (Wadler 1998)

objetos tipos algébricos
nova variante fácil difícil
nova operação difícil fácil

O expression problem (ou problema da expressão), cunhado por Philip Wadler em 1998, é um dilema clássico de design e sistemas de tipos em linguagens de programação. Ele descreve a dificuldade de extender um sistema em duas dimensões ortogonais: novos tipos de dados vs novas operações, sem modificar o código existente e mantendo a segurança de tipos estática (em tempo de compilação).

Voltaremos a mencionar este problema no final da unidade 8, quando já tivermos visto sistemas de tipos. Isso nos permitirá ainda discutir possíveis alternativas ao problema que LPs reais atuais procuram adotar.

⏱ 5 min.

Cada estilo é fechado em uma dimensão e aberto na outra. O dilema completo exige extensão sem alterar o código existente e sem perder verificação de tipos (na formulação original, estática); só fará pleno sentido depois da Unidade 8, onde voltaremos ao problema.

Qual evolução é mais comum? Depende do domínio: compilador (linguagem estável, análises se multiplicam) favorece tipos algébricos; interface gráfica (componentes se multiplicam) favorece objetos.

Garantias: com tipos algébricos e dados imutáveis, é mais fácil raciocinar sobre todos os casos. Com objetos e estado mutável, o comportamento depende do objeto e do seu estado, o que dificulta raciocínio e testes.

Soluções reais, só menção: Visitor (Java), traits (Rust, Scala), type classes (Haskell), protocols (Swift), functools.singledispatch e protocolos em Python (sem verificação estática); interfaces Java resolvem parcialmente.
